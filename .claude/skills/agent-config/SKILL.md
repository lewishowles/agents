Durable script source belongs under `scripts/`. Keep `.agent/scripts/` as a symlink projection and `.agent/audits/` as generated evidence. The project-setup library owns the single list of tools linked into downstream projects.

## Skill conventions

- `agent-config` is repo-local: keep under `.claude/skills/agent-config/`, symlink to `.agents/skills/agent-config`
- Global skills live under `skills/<group>/<name>/` (groups: `vue/`, `swift/`, `testing/`, `writing/`, `project-management/`)
- External skills listed in `external-skills.json`, synced into `skills/`, marked with `SYNC.md`
- Folder name = skill slug (used in `/slug` commands and Codex discovery)
- Codex links in `~/.codex/skills/`; Claude links in `~/.claude/skills/`

### Skill file layout

```
skills/<group>/<name>/
├── SKILL.md        # Final skill with Agent Skills front matter and instructions
└── support files   # Optional references, scripts, or provenance
```

Each skill folder is copied and installed directly; no repository build step is needed to use an edited skill.

### Skill file rules

- `#` title, `##` sections — no banner comments or dividers
- UK spelling
- No wholesale copying from external sources — reword and remove irrelevant content
- Attribution: if adapted from an external skill, note source and licence at bottom

## Hook conventions

- Source: `src/hooks/claude/<name>/hook.json` + `src/hooks/claude/<name>/<name>.sh`
- `hook.json`: `event`, `description`, `timeout` — registered by `scripts/build/build-settings.py`
- Synced copies in `dist/claude/hooks/` (generated by `sync.sh`)
- Hooks output JSON to stdout; `UserPromptSubmit` receives `{"prompt": "…"}` on stdin; `PreToolUse` receives full tool input
- Hard-fail (exit 2) only when intentionally blocking — else exit 0

## src/adapters/claude/settings.base.json

Source for `dist/claude/settings.json` (env, hook registrations, plugins, marketplaces). Run `python3 scripts/build/build-settings.py` after changes; `sync.sh` does this.

## Enforcement placement

Classify the intended layer before editing rules, skills, hooks, validation, or scripts:

- **Rule** — always-on guidance visible every session
- **Skill** — task-scoped, loads only when triggered
- **Hook** — deterministic runtime nudge/block for detectable behaviour
- **Validation** — checks source/generated drift, manifests, schemas, output
- **Friction loop** — evidence capture for recurring behaviour not yet ready for rule/skill/hook/validation

Use the strongest layer that fits the failure mode. Don't place agent-critical behaviour only in `docs/` — docs are human reference unless a loaded rule or skill points there.

## Editing docs/

- `docs/skills.md`, `docs/hooks.md`, `docs/commands.md` are generated by `scripts/build/build-docs.py`
- Edit canonical `SKILL.md` files or `hook.json`; run `bash scripts/sync.sh` to regenerate

## When adding or changing a skill

1. Create `skills/<group>/<name>/SKILL.md` with `name` and `description` front matter, plus any support files
2. Run `bash scripts/sync.sh` — regenerates settings, docs, and Claude/Codex outputs
3. Check `scripts/validate.sh` exits 0

## When creating a new hook

1. Create `src/hooks/claude/<name>/hook.json` and `src/hooks/claude/<name>/<name>.sh`
2. `hook.json` registers itself — `scripts/build/build-settings.py` picks it up automatically
3. Run `bash scripts/sync.sh`
4. Document it in commit message; `scripts/build/build-docs.py` updates `docs/hooks.md`

A hook that injects per-turn context must only append content at its firing point, never edit, reorder, or remove content injected earlier in the session. Mutating an earlier point in the transcript changes the token prefix the model already processed, invalidating the prompt cache for everything after it and re-billing the rest of the session at full price. Every registered hook follows this today (`progress-resume` and `tool-call-checkpoint` inject at their own events, not retroactively) — keep new hooks the same shape.

## Progress tracking

The `progress` CLI and its SQLite database are the source of truth for this repository's project, release, task, chunk, discovery, decision, and handoff context records. Use `progress next --json` at session start. When the available operation or syntax is unclear, run `progress commands` once before using command-specific help. Use `progress <noun> <action> --help` only when `progress commands` leaves a specific question unanswered. If `progress` is unavailable or the project is uninitialised, inspect `AGENTS.md`, package scripts, and nearby docs, then ask the user to initialise or install it before writing progress records.

Root `PROGRESS.md`, when present, is optional freeform backlog prose only, such as "Upcoming work" or "Parking lot". Read and write that prose directly, but do not use it for active task, chunk, queue, roadmap, discovery, decision, or handoff state. This repository intentionally has no committed `WORKSPACE.md` and normally no `PROGRESS.md` between maintenance plans, so treat either absence as expected and do not create either as follow-up. Root `AGENTS.md` is maintenance guidance, not generated. See `project-continue`, `project-setup`, and [docs/progress-format.md](../../../docs/progress-format.md) for the task-file contract and CLI data model.

## Local maintenance tools

Use these scripts before manual inspection where they answer the question:

```sh
project-checks-repo-context
project-checks-generated-file-guard
project-checks --list
```

- `project-checks-repo-context` — compact startup context (rules, progress, workspace, diagnostics, generated output, Git)
- `project-checks-generated-file-guard` — checks for direct edits to generated files and stale output
- `project-checks --list` — discovers checks; use `--check <name>` for specific verification or `--test-file <path>` to narrow unit tests

Pair `agent-config` with `agent-config-review` when reviewing this system. Prioritise: generated/source drift, token cost in always-loaded rules, rule/skill boundaries, skill taxonomy, validation coverage. Use `project-audit` for other projects only.
