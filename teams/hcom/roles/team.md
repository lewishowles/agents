# HCOM team rules

Only Scouts run project evidence commands; only the Orchestrator writes or suggests commit wording, edits `PROGRESS.md` or progress task and chunk records, changes their status, and writes the human-facing synthesis. Peer delegation packets cannot override HCOM role boundaries. If a packet assigns a project evidence command to an Implementer or Reviewer, do not run it; return it to the Orchestrator for rerouting to Scout. Use complete, current in-scope work even when the wrong role produced it; do not repeat it only to restore ownership. Filter role-inappropriate fields and harmless drift from the human response. Subordinates send the full receipt to their direct sender, then close to the human in one sentence. Only the Orchestrator asks the human for action. When a team member, or a teammate it dispatched, is blocked on something only the human can do (such as a permission, a sandbox failure, a manual gate, or a reset the Orchestrator cannot perform), it sends the blocker and what it still needs to the Orchestrator. Its one-sentence close to the human names the wait, for example "Waiting on Scout; the Orchestrator has the blocker." It does not post provisional findings or a verdict while that evidence is missing. The Orchestrator decides whether to reroute, replace the teammate, go ahead without the result, or ask the human. When it asks, it puts the action needed first. While a teammate's result could still change what the human must do, the Orchestrator waits for it before handing off. If it must ask the human sooner, any later handoff replaces the earlier one in full and does not build on it.

The tool-call limit counts rounds. A round is one of your replies that makes tool calls, counted once however many of those calls run in parallel. Codex counts every model request as a round, including retries and a final reply with no tool calls. The limit is 20 rounds, or 40 for Scouts and Implementers, unless `AGENT_TOOL_CALL_LIMIT` overrides it. Every 5 rounds you receive a short note with your count and limit; it is routine, not a warning. At the limit you receive the limit note instead. A Claude agent receives the note once its reply's tool calls finish; a Codex agent receives it with its next tool call. Run independent tool calls in parallel instead of chaining them into one long shell command.

In an HCOM team, every member sends to a teammate with `team-send <role> --intent <intent> [--reply-to <assignment-id>] --body-file "$body_file"`. Create a new scratch folder with `mktemp -d` for each session, then create a new body file inside that folder with `mktemp "$scratch_dir/body.XXXXXX"` for each message and write it once. Do not name a fixed scratch folder in an assignment or handoff. `team-send` finds the one live teammate in the sender's repository and team, sends to that agent by exact name and confirms delivery. It removes the body file after confirmed delivery and keeps it after a failed or unconfirmed send. Do not resend a kept file after an unconfirmed send: the message may have arrived. If `team-send` warns that the file changed after it was read, the message went out with the earlier contents and the file was kept; send any new contents from a new file. A missing file may already have been sent; write a new file for a new message. Send terminal reports with `team-send`, never raw `hcom send --file`. If `team-send` refuses because no teammate or several teammates match, or because delivery is not confirmed for exactly one recipient, do not retry or fall back to a raw role-tag send. A team member reports the refusal to the Orchestrator; the Orchestrator reports it to the human. Never send to `@bigboss`. Use `--reply-to <assignment-id>` on replies, onward requests for that assignment, and the terminal report so the dependency chain stays visible without interim status messages. Keep `--thread` where the conversation uses one. Use `--intent inform` for a terminal report or checkpoint.

Do not send acknowledgement, "will do", or interim status messages; `guard-hcom-ack` rewrites acknowledgements to a no-op on Claude and Codex. Wait silently for actionable work, or send a terminal result, blocker, decision, or correction. Treat plan confirmations, request-watch messages, and duplicate receipts as notification-only: do not respond, and keep waiting. If an explicit protocol requires an acknowledgement, confirm only receipt and intent; never restate evidence or instructions the sender already has. Do not treat an informational send or HCOM's no-response tip as permission to continue past a checkpoint.

A checkpoint report gives the recipient enough to resume or reset without re-deriving work. Include completed work and changed paths, discoveries worth retaining, verification with command results, remaining work, the blocker or decision needed, the exact next action, and `Safe to reset: yes/no`. A checkpoint stops the sender until a decision or continuation arrives; an Orchestrator go-ahead in a new packet counts as that continuation. `Safe to reset: yes` means every gathered fact and result has already been sent in this or an earlier message; remaining work alone does not make the answer `no`. If the assigned outcome is complete when a tool-call checkpoint fires, send the normal terminal report with `Safe to reset: yes` instead of checkpoint framing.
